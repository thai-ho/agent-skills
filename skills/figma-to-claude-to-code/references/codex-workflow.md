# Codex: implement an approved contract

Invocation from a target frontend repository: `$figma-to-claude-to-code ./private-design-contracts/checkout/`

1. Require the explicitly named, readable contract and all listed assets. Do not substitute remembered conversation content or an unmentioned nearby directory. Run `node scripts/validate.mjs /absolute/path/to/contract`. Stop design edits on `invalid` or blocking design issues. A structurally ready package does not prove organizational authorization; respect the user's actual transfer permission.
2. Read target repository instructions and inspect Git state, routes, architecture, themes, tokens, component APIs, existing states and functional logic, commands, fonts, test data, browser setup and screenshot tooling. Resolve relevant Figma components and tokens to existing repository code. Record import paths, props, variants and evidence in a separate mapping report. Flag conflicts and missing mappings.
3. Present a concrete plan: affected files/routes, reuse strategy, any justified new foundation, required states/modes/viewports, missing context, functional boundaries, capture setup and verification. Obtain implementation approval unless the same concrete plan was explicitly approved in this session. Package-building approval is a different boundary.
4. Implement the approved scope using repository conventions, existing business behavior and original assets. Do not invent token values, approximate icons or application rules absent from the contract. Keep contract files and Figma baselines read-only.
5. Run applicable lint, typecheck and functional tests. Capture deterministic browser screenshots for every required present coverage item at declared viewport/device scale, mode and state. Use known fonts and stable UI data, disable animations and wait for fonts and assets. Record settings. Compare each capture to its Figma PNG using `scripts/visual-diff.mjs`, and separately audit component, token and asset usage. Pixel similarity alone does not verify correct design-system use.
6. Classify differences. Fix implementation-side deviations and rerun at most three automatic fix/verify iterations per validation run. Escalate sooner when the missing fact belongs to Figma or to product requirements. Emit `feedback.json` in a separate validation directory with stable issue IDs, referenced contract ID/revision/manifest hash, observed versus expected evidence, questions and artifact hashes. Validate it with `scripts/validate.mjs CONTRACT --feedback FEEDBACK [--previous-feedback PREVIOUS]`.
7. Ask the user to transfer feedback to Claude for design-side correction; Claude creates a new revision. Revalidate that revision before continuing. Do not modify a baseline to make the implementation pass.

Report each gate as passed, failed, blocked or not verified. Browser visual verification requires actual reference PNGs, fonts, deterministic state/data and usable capture tooling. After acceptance, a target project may add Playwright `toHaveScreenshot()` regression baselines; a fresh browser snapshot is not proof of a Figma match. Live evaluation on an authorized component, single screen and multi-screen feature is required before calling the package v1.0 ready.
